## 未验证项与风险

- **L4 增量更新（4.2.2 → 4.3.0）**：本轮不在 L3 内 —— 更新器的下载源是
  `releases/latest/download/FuFumidi.Install.exe`，必须先把 4.3.0 的 Release 资产上传才有得可更。
  上传后单独跑，结论并入本报告（见文末补记）。
- **UTAU 合成渲染 / 声库切分**：未在 VM 内实跑（需要先上传音频做声库切分，链路长且耗时）；
  本版未改动 UTAU 相关代码，风险低。引导中该章 2 步已按 SKIP 如实标注。
- **模型下载**：未在 VM 内实跑（需外网 + 大流量）。出厂依赖自检已覆盖「不下载模型也能用」的路径。
- 已知环境限制（非产品缺陷）：
  - 卸载后残留 `resources\python` 7 个文件 + 1 个孤儿 `python.exe`。触发条件是**测试脚本强杀主进程**
    （`Stop-Process -Force`）——引擎子进程来不及随之退出，文件被占用删不掉。真实卸载路径（用户关闭
    程序或不关时由卸载器提示结束进程）不会走到这里；记录在案以便后续加一层「卸载前回收引擎子进程」。
  - VirtualBox NAT 会静默回收空闲 TCP，宿主机经反向隧道驱动 guest 界面的**长求值（>30 s 静默）响应会丢**：
    脚本其实已经在页面里跑完，只是结果回不来。对策是把结果挂到页面 `window` 上，再用一次短求值取走
    （本轮转录、多语言、主题等长探针均按此写）。
  - 走查经隧道跑到第 11 章时连接被回收过，因此 `cdp-guide-walk.cjs` 增加了 `WALK_FROM` / `WALK_TO`
    章节区间参数，可从断点续跑而不是整轮重来。

## 补记：L4 增量更新（4.2.2 → 4.3.0）

前置：4.3.0 的 Release 资产已上传（`releases/latest/download/FuFumidi.Install.exe` 指向本版）。

流程：干净基线 → 静默安装 4.2.2 → 首次启动 → 在 `FuFumidiData` 里埋两个标记文件
（`cache\l4-keep-marker.txt` 文本 + `midi\l4-dummy-song.mid` 4 KB 二进制）→ 记录数据目录文件数
→ 应用内「检查更新」→ 触发更新器 → 更新器替换文件 → 复核（含自动重启）。

> **关键前提**：自动重启由**发起更新的那个版本**里的守护逻辑驱动 —— 升级包里的新代码要等
> 更新结束、新版本跑起来才生效。因此本轮分两条路径各测一次：
> ① 真实用户路径 **4.2.2 → 4.3.0**；② 本次修复之后的路径 **4.3.0 → 4.3.0**（同版本号复更，
> 只为验证新守护逻辑本身）。两条结论不同，都如实记录。

### 本轮 L4 挖出的真实缺陷（已在 4.3.0 内修掉）

**现象**：应用内更新能完成文件替换，但主程序不会自动回来，用户只看到一个停在完成态的更新器窗口。

排查过程与三个独立根因（每一个单独都足以让重启失效）：

| # | 根因 | 怎么发现的 | 修法 |
|---|---|---|---|
| 1 | **调用顺序**：旧写法是「起守护进程 → 探测下载源 → 起更新器」。探测要走最多约 24 s 的 HEAD 请求，守护进程第一次查询时更新器还没出现，把「还没起」误判成「已结束」，提前拉起旧版主程序 —— 随即被更新器杀掉，真正替换完成后再也没人重启它 | 时间线显示 `updater` 出现前 `app` 就被拉起过 | 改为先探测源 → 起更新器 → 起守护进程；守护进程另加「先等更新器出现（最多 90 s）再等它退出」 |
| 2 | **detached 的 PowerShell 不执行脚本**：`detached:true` + `powershell.exe -File` 一秒内退出、退出码 0、脚本一行都没跑（宿主机与虚拟机均可复现，与脚本内容无关）；而不 detached 的子进程又会随主进程结束，两条路都走不通 | 主进程日志显示 `guard spawned pid=…` 紧接着 `guard exit code=0`，而守护日志里连第一行 `[guard] start` 都没有 | 改用 WMI（`Win32_Process.Create`）拉起守护进程：它挂在 `WmiPrvSE` 下，既不在本进程进程树里、也不带 `DETACHED_PROCESS`，PowerShell 能正常执行脚本 |
| 3 | **模板字符串吃掉反斜杠**：守护脚本里 `Join-Path … 'resources\app.asar'` 的 `\a` 被当转义吃掉，生成出 `resourcesapp.asar` —— 那个「等 asar 写稳再启动」的检查一直空转 | 把 guest 里生成的守护脚本取回来逐行读，发现路径是 `resourcesapp.asar` | 生成脚本改用 `String.raw`，并去掉路径两侧多余的 `\\\\` |

同时补了可观测性：整条更新流程（主进程探测源 / 起更新器 / 起守护 + 守护的等待与启动）
都写进 `<数据目录>\temp\fufumidi-restart.log`。修复后该日志完整覆盖全流程：

### 说明：本版仍走全量下载

`build-kachina.ps1` 支持 `-OldDirs` 生成差分补丁，本轮**未使用**（4.2.2 的 `win-unpacked`

「更新器 + 全量离线包（124.6 MB）」，更新器仍会做 Range 分块下载与进度显示。
差分补丁可在下次发布时用干净的旧版目录重新引入。
