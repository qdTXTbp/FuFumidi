**第一次尝试的失败与结论（重要）**：用 `--source ghfast-beta` 时更新器跑了 10 分钟未完成（ghfast.top 实测 0.25 MB/s，且当时宿主正在上传 674 MB 安装包抢占带宽），守护进程按 10 分钟超时逻辑先拉起了旧版。
换 `ghproxy-net-beta`（实测 0.87 MB/s）后一次通过。**这不是产品缺陷**，但说明弱网下「差分下载」的体验取决于镜像速度；`pickUpdateSource` 只做 HEAD 可达性探测，不测速。

**已知行为**：更新器完成后窗口会停在完成态，需用户关闭（或等守护 10 分钟超时）才会拉起新版主程序 —— 与 4.3.0 报告的观察一致；本次为让守护逻辑尽快继续，脚本主动结束了更新器进程。


## 4. 发现的问题

1. ~~**CNB 测试通道镜像仍是 beta.1**~~ → **已解决**。
   处理前：`.../releases/download/beta/FuFumidi.Install.exe` = 143,674,067 B（beta.1），而应用在国内偏好下**第一个就用 CNB**（`main/update.js` 的 `orderedUpdateSources`），HEAD 探到 200 即选中 → beta 通道用户会被装回 beta.1。
   原因：`cnd\令牌.txt` 里原令牌是**只读**的（探针证据：`GET /releases/tags/beta` → 200，`POST /asset-upload-url` → 403 `Missing required scopes: repo-release:rw`，`GET /user` → 403 `account-profile:r`）。
   处理后：用该文件里第二个带写权限的令牌跑 `scripts/cnb-upload.py --tag beta`，上传 `FuFumidi.Install.exe`（151.0 MB / 59 s）、`latest.yml`、`FuFumidi.update.exe`，**成功 3 / 失败 0**；复查 `cnb beta Install = 158,368,964 B`（与本地产物同尺寸）、`latest.yml` 返回 `version: 5.0.0-beta.2`。
   随后在虚拟机里用 `--source cnb-beta` 完整跑通增量更新（见 L4-C）。
2. `engine/tests/test_engine_openutau_cli.py` 在中文控制台下会因 `UnicodeDecodeError: 'gbk' codec`（子进程输出解码）失败 —— **测试脚本自身缺陷**，设 `PYTHONUTF8=1` 后 18/18 通过。
3. **建议加固（未改代码）**：`pickUpdateSource()` 只做 HEAD 可达性探测，不校验镜像上的包与目标版本是否一致 —— 这次就是「可达但过期」的 CNB 压过了新鲜的 GitHub 镜像。可在 beta 通道下要求候选源同时提供 `latest.yml` 且 `version:` 与目标一致（CNB beta 此前正是 404，会被自然跳过）。
4. `engine/tests/test_openutau_core_matches_source.py` 需要上游 C# 参考仓 `D:/FuFuMIDI/_ref/OpenUtau`，本机不存在 → 无法运行（脚本在缺失处 `FileNotFoundError`）。
5. `scripts/vm/guest-run.ps1` 用**相对路径**传 `-ScriptPath` 时会静默跑到 guest 里残留的旧 `run.ps1`（脚本把 `copyto` 的报错 `Out-Null` 掉了）。本次测试改用绝对路径规避；建议在 `copyto` 后校验 guest 侧 `run.ps1` 的哈希。
6. `release/win-unpacked` 里给测试版建的 `FuFumidiData` junction 会被 electron-builder 的 NSIS 步骤**跟进去压缩**（日志里出现 `Compressed "FuFumidiData/..."`）。本次曾因此中断一次打包；正确做法是**打包全部结束后**再建 junction。
