# V0.2 导出格式补齐与文案对齐（2026-11-15）

## 决策

`docs/plans/2026-11-15-workstation-roadmap.md` 的 V0.2 与「待拍板项 3」原本是二选一：
补 MP3/FLAC 编码，**或**把 README 文案改回实际支持的 WAV。用户拍板 **「都要」**——
既让宣传成真，也把全仓口径对齐，不留「文档写一套、代码做一套」。

## 实现

### 架构

```
渲染进程 encodeWav → 24-bit WAV 母版 bytes
      ↓ bridge.exportAudio (IPC，含 format / ext / 元数据)
主进程 main/export.js → main/audio-encode.js → 包内 ffmpeg 转码
      ↓ 压缩后 bytes
writeExport：原子写 + sidecar manifest（与 WAV 完全同一条落盘链路）
```

- 选在主进程转码：渲染进程没有编码库，不值得为 MP3/FLAC/OGG 引入 WASM 依赖；
  安装包本就带 `imageio-ffmpeg`（MP4 导出已依赖），实测含
  `libmp3lame` / `flac` / `libvorbis` / `libopus`。
- ffmpeg 定位沿用 `main/video.js`：`imageio_ffmpeg.get_ffmpeg_exe()`，**不硬编码版本或系统 PATH**。
- 压缩格式统一走 **24-bit WAV 母版**（避免 16-bit 二次损失），`bitDepth` 字段对压缩格式
  表示母版位深；dither 开关按 `bitDepth === 16` 自动禁用。
- 转码失败会让 task center 收到 `fail()`，不会静默落一个扩展名与内容不符的文件。

## 边界与未覆盖

1. **分轨 ZIP**（`export:stems-zip`）仍只打包 WAV；本次只改主导出 `export:audio`。
2. **歌声工作台的 WAV 导出**走另一条链路（`main/utau.js` 等），不受影响。
3. **转码耗时没有接进度**：task center 目前只在结束时 `progress(1)`，长曲目转码时任务卡会停在初始状态。
   若要补，应在 `encodeAudio` 里加进度回调（ffmpeg `-progress pipe:1`）。
4. **manifest 的 `audio.bitDepth`** 对压缩格式记录的是母版位深（24），不是成品位深；
   `audio.format` 已是 `mp3/flac/ogg`，可据此区分。
5. **未做 UI 真机实测**：下拉选项渲染、保存对话框扩展名过滤、实际点一次导出，都还没在应用里走过。
   建议 V0.1 收口时一起冒烟。
