> 「FuFumidi-vio.mp4 和工具可视化呈现的效果差了十万八千里，而且导出时压力太大，导致我电脑崩溃重启了一次」

曲目 `E:\Midi\midi\原神-闪耀的群星\Exclusive Specialty 独家特调 - 陈致逸 _ HOYO-MiX.mid`（4 轨，1:10）。

## 一、根因：导出把**物理像素**当成了**逻辑单位**

瀑布流的几何里有一批**绝对像素**常量，它们只在「画布逻辑尺寸 ≈ 实时画布」时才成立：

| 常量 | 值 | 出处 |
|---|---|---|
| 琴键条高度 | `min(120, 0.2·h)` | `core/viz.js` `drawVizWaterfall` |
| 滚动速度 | `120 px / 小节` | 同上 `const v = 120 / barSec` |
| 音符圆角 / 最小厚度 | 4 / 5 px | 同上 |
| 起音发光半径 | `20·near` px | 同上 |
| 小节号 / C 键字号 | 10 px | 同上 |

实测实时画布（1920×1080 窗口、瀑布流模式、dpr 2.5）是 **934×534 CSS / 2335×1335 物理**。
导出侧却直接 `cv.width = W` 再把 **3840×2160 物理像素当逻辑单位**画 —— 常量相对画布小了 **4 倍**：

| | 实时（934×534） | 导出（3840×2160 当逻辑） | 比值 |
|---|---|---|---|
| 琴键条占画面高 | 106.8 / 534 = **20.0%** | 120 / 2160 = **5.6%** | 0.28× |
| 一小节滚动 120px | 一屏 4.4 小节 | 一屏 **18 小节** | 4.1× |
| 音符宽（1 个白键） | 18.0 / 934 = 1.93% | 73.8 / 3840 = 1.92% | 1.0× |
| 音符厚（同样的时值） | 更高 | 细 1/4 | 0.25× |

外加背景图的 cover 缩放：实时是 `max(934/2560, 534/1440)=0.387`，导出是 `1.5` —— 底图被放大了 3.9 倍。
**三处叠加，就是用户看到的「细缝琴键 + 满屏细丝音符 + 放大糊掉的底图」。**

### 修复

`core/viz.js` 新增 `VIZ_REF_H = 540`（对齐实时瀑布流画布的 534）与 `VIZ_REF_DPR = 2.5`；
导出与**导出预览**都改成「逻辑高度固定 540、用 `ctx.scale` 映射到物理缓冲」：

```js
const dscale = H / VIZ_REF_H;          // 4K → 4.0；1080P → 2.0
ctx.save(); ctx.scale(dscale, dscale);
drawVideoFrame(ctx, W / dscale, VIZ_REF_H, tick, s, buf, vf, el);
ctx.restore();
```

物理缓冲仍是 `W×H`，**录制流与 ffmpeg 转码的分辨率不变**（早期把物理缓冲放大 ×EXPORT_SCALE 会导出失败）。
逻辑尺寸因此与实时几乎相等：导出 960×540 vs 实时 934×534（宽 +2.8%、高 +1.1%）。

顺带把背景**模糊半径**按 `物理像素 / 2.5` 等比换算：`filter` 的模糊是**设备像素**量（实测不随 CTM 缩放），
照抄 13px 在高分辨率帧上会明显更清晰 —— 那也是「不是一幅画」。

## 二、根因：导出的能量包络整段是 `NaN`（背景脉动光晕从来没有过）

`smoothEnergyDt(prev, target, dt)` 少了非数值兜底：导出每次开录都把 `_state` 清空，第一帧 `prev === undefined`，
`undefined + (x - undefined)·a` = `NaN`，而 `clamp01(NaN)` 仍是 `NaN`，于是 `energy > 0.01` 永远为假 ——
**从第一帧到最后一帧都没有那层随音乐起伏的背景光晕**。实时侧用的 `smoothEnergy` 一直有兜底，所以只有导出缺这一层。

修复：与 `smoothEnergy` 对齐，`prev` / `target` 非有限值一律按 0 处理。

## 三、负载：每帧都在重新模糊一张满幅底图

`paintVizBg` 原来每帧执行：cover 缩放 + `filter: blur(13px)` 画满整帧。
4K 下一次 `drawImage`（含模糊）实测 **30–35 ms**，而导出是**实时录制**，24fps 的单帧预算只有 **41.7 ms**；
再叠加 VP9 编码（8 Mbps、4K）与随后的 x264 转码 —— 整段导出期间 CPU 持续满载，机器崩过一次。

### 修复

`paintVizBg` 增加**设备分辨率离屏位图缓存**：背景参数（模式/颜色/模糊/暗化/图片/画布尺寸）在一次会话里恒定，
烘一次之后每帧只做一次 `drawImage`。缓存是在 `ctx.scale(sc, sc)` 下画的，模糊与 cover 语义与直画**逐像素等价** ——
实测实时画面在改动前后 **PSNR = inf（逐位相同）**。

同时：

* 录制开始前**预热**背景缓存（否则第一帧要现烘，正好落在录制器冷启动窗口里）；
* 默认帧率 30 → **24 fps**；
* 导出时长硬上限 **120 s**（超出截断并 toast 提示分段导出）；
* 选择 4K 时给出负载提示。

## 四、验收

同一内容时刻（t = 25 s）、同一曲目，把「实时画布」与「导出链路渲染的一帧」叠在一起比对
（`live_wf_25.png` vs `exp_final_1080_25.png`）：

* 琴键条高度与位置、C1–C8 标注一致；
* 音符块的位置、宽度、厚度、配色、发光一致；
* 小节线与小节号（12–15）一致；
* 底图裁切与相对模糊一致；
* 实时侧改动前后 PSNR = inf（背景缓存没有改变实时观感）。

单帧绘制耗时（`getImageData` 强制冲管线后的真实值）：1080P ≈ 11 ms、720P ≈ 7 ms、4K ≈ 44 ms。

## 五、遗留与建议

* 导出是**实时录制**：成片多长，就必须以这个负载跑多久。4K 长片建议改用 **1080P** 或分段导出。
* 想彻底摆脱实时约束，需要把录制链路换成 **WebCodecs `VideoEncoder` + 显式时间戳**（离线按帧编码），
  那是另一次改动，未包含在本次修复里。
* 仪表盘模板的实时卡片是 934×300，导出卡片约 932×334（垂直多 ~11% 的时间窗）；
  若要严格一致，需要把仪表盘的 `pad=14 / panelH=178` 也做成按参考高度推导。
