# V0.1 收口：提交方案与安全告警（2026-11-15）

## 一、⚠️ 头等事项：CNB API token 明文泄露（与本次提交无关，但必须先处理）

体检工作区时发现 `scripts/publish-*-cnb.js` 系列把**同一个 CNB API token 硬编码**在源码里
（`const TOKEN = '…'`，出现在第 7 或 9 行；本文不复述具体值）。

| 范围 | 数量 | 状态 |
|---|---|---|
| 含明文 token 的 CNB 发布脚本 | **12 个**（6.4.4 / 6.4.5 / 6.4.6 / 6.4.7 / 6.4.9 / 6.5.0 / 6.6.0 / 6.6.1 / 6.6.2 / 6.6.3 / 6.7.0-beta.1 等版本的 `-cnb.js`） | 全部未提交或已入库，见下 |
| **其中已被 git 跟踪** | **2 个**：`scripts/publish-6.4.4-cnb.js`、`scripts/publish-6.4.5-cnb.js` | ⚠️ 说明该凭据**很可能已进入 git 历史** |
| GitHub 版脚本 | 用 `process.env.GH_TOKEN`，无硬编码 | 安全（但仍排除在本次提交外，保持发布资产整组处理） |

`git ls-files "scripts/publish-*"` 共 4 个已跟踪文件（6.4.4 / 6.4.5 的 cnb + github 两对）。
若仓库曾推送到远端，这 2 个文件里的 token **视同已泄露**。

### 建议处置顺序

1. **立刻在 CNB 平台撤销并重新生成该 token** —— 改代码不能让旧凭据失效，这一步不可替代。
2. 12 个脚本统一改成 `const TOKEN = process.env.CNB_TOKEN;`，缺失时明确报错退出；
   发版用 `CNB_TOKEN=… node scripts/publish-<ver>-cnb.js [文件名…]`。
   可参考同目录 `cnb-mirror-releases.js` 已有的环境变量口径。
3. 若仓库公开或曾被他人克隆：确认历史暴露范围，必要时用 `git filter-repo` / BFG 清理这 2 个文件
   并协调强推（会改写历史，需所有协作者配合）；仓库私有时可只做轮换。
4. 处理完再单独提交这些发布脚本，不要混进功能提交。

> 本次提交**排除全部 `scripts/publish-*.js`**，不把新的凭据副本带进版本历史。
> 这些脚本改动由你决定，我没有擅自改写发版工作流。

## 二、构建产物（第二个误提交风险）

`git status` 里长期裸露 20+ 个 `release-*` 目录：`release-6.4.3/`、`release-6.4.3b/`、
`release-643/`、`release-pack/`、`release-unpacked6..14/` 等。
抽样 `release-6.4.3/` 就有 **350 MB**（`du` 扫到一半被中断，总量更大）。
原 `.gitignore` 只覆盖 `release/`、`release-unpacked2..5/`、`release-beta/` 等少数精确名字。

本次补三条规则（物理文件保留，不删除任何东西）：

```
release-[0-9]*/
release-unpacked[0-9]*/
release-pack/
```

## 三、提交分组决策

**只做 1 个本地提交，不 push。** 原因：

- 原本想按「6.6.3 / 6.7.0-beta.1 / V0.2 / V0.3」拆多个提交，但
  `main.js`、`preload.js`、`frontend/src/App.vue`、`frontend/src/styles/tokens.css`、
  `frontend/src/core/changelog.js` 等文件**同时含有多组改动的 hunk**；
  项目无 pre-commit hook，但按文件拆分会产生「单独 checkout 就跑不起来」的中间提交
  （例如 `main/export.js` 需要 `main.js` 注入运行时，两者分家会让压缩格式导出失效）。
- 精确按 hunk 拆分需要交互式 `git add -p`，本次不采用。
